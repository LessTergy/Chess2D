# AGENTS.md

Инструкции для AI-агентов, работающих с проектом `Chess2D`.

## Язык и коммуникация

- Общайся с пользователем на русском. Имена классов, методов, полей, файлов, пространств имён и публичных API оставляй на английском.
- Добавляй комментарии на английском, только если они объясняют решение или ограничение, которое трудно понять из кода.

## Область проекта

- Основной код находится в `Assets/Scripts`, вспомогательные UI-компоненты в `Assets/Libs`, основная сцена в `Assets/Scenes/Main.unity`.
- Версию Unity бери из `ProjectSettings/ProjectVersion.txt`, зависимости проекта проверяй в `Packages/manifest.json`.
- Сгенерированные и временные директории Unity (`Library`, `Temp`, `obj`, `Logs`) не редактируй вручную.

## Выполнение задач

- При реализации и ревью применяй Ponytail уровня `full`, если пользователь не выбрал другой уровень или не отключил его. Выбирай самое простое решение, которое полностью закрывает требования и учитывает стоимость сопровождения.
- Перед существенной реализацией определи, где сейчас находится изменяемое поведение, и проверь, можно ли решить задачу одной общей правкой. Добавляй новый слой или генератор только при конкретной необходимости.
- Перед правкой получи полный затрагиваемый фрагмент. Если вывод обрезан, уточни запрос к источнику.
- Запрос на анализ, ревью или планирование ограничивает работу соответствующим этапом. Изменения в проект вноси в рамках порученной реализации.
- Уточняй требования, когда от ответа зависит выбор между несовместимыми реализациями. Некритичные детали решай разумным допущением и сообщай о нём, если оно влияет на результат.

## Анализ кода через MCP CodeGraph

- Перед выводами, рекомендациями, планированием, ревью или изменением кода проекта сначала выполни релевантный запрос к CodeGraph. Для каждого нового вопроса о коде делай отдельный запрос к проекту Chess2D.
- Определи затрагиваемые файлы и символы, их зависимости, цепочки вызовов и область влияния. Уточняй недостающие детали чтением файлов и другими инструментами.
- Если CodeGraph недоступен или индекс не содержит затрагиваемый код, останови зависимую работу по этому коду и сообщи, что нужно восстановить. Для задач по документации и настройке инструментов, где анализ кода не нужен, используй подходящие инструменты без запроса к графу.

## Документация через MCP Context7

- Используй Context7, когда пользователь спрашивает о библиотеке, фреймворке, SDK, API, CLI или облачном сервисе, а также при работе с новым или зависящим от версии Unity API. Это касается синтаксиса, настройки, миграции между версиями, установки, использования CLI и ошибок, связанных с конкретной библиотекой. Для задач по существующему коду сначала определи задействованные символы и зависимости через CodeGraph. Для документации предпочитай Context7 веб-поиску.
- Начни с `resolve-library-id`, указав название библиотеки и вопрос. Если пользователь уже указал точный ID в формате `/org/project`, используй его. При выборе результата учитывай совпадение имени, релевантность, надёжность источника, число примеров и оценку. Если результаты не подходят, уточни запрос или название библиотеки. Используй ID нужной версии, когда она указана.
- В `query-docs` передавай выбранный ID и конкретный вопрос. Запрашивай отдельные темы по отдельности, если вопрос не касается их взаимодействия. Основывай ответ на полученной документации. Если Context7 не возвращает официальный первоисточник, сверяйся с официальной документацией или явно обозначь ограничение.
- Рефакторинг, написание скриптов с нуля, отладка бизнес-логики, ревью кода и общие вопросы программирования сами по себе не требуют Context7.

## Общие принципы и стиль C#

- Применяй KISS, DRY и YAGNI. Используй SOLID там, где это упрощает структуру. Переиспользуй существующие методы, типы, общие ассеты и базовые префабы с учётом поведения всех потребителей.
- Используй фигурные скобки в управляющих конструкциях, включая однострочные. Для обычных методов и свойств с блоковой логикой используй скобки. Expression-bodied members применяй там, где это соответствует стилю файла и остаётся читаемым.
- Для локальных переменных по умолчанию используй `var`. Указывай тип явно, если `var` неприменим или тип важен для понимания кода.
- Для приватных полей предпочитай `_camelCase` и учитывай сложившийся стиль файла. Сохраняй существующие пространства имён и структуру папок.
- Сериализуй приватные поля через `[SerializeField] private`. Для чтения извне добавляй публичное свойство только для чтения, когда оно нужно.
- Связывай внешние зависимости через Inspector или существующий код сборки объектов. Для компонента того же объекта допустим `GetComponent`. Избегай поиска зависимостей во время выполнения через `Find`, `FindObjectOfType` и схожие API.
- Ошибки обязательной настройки должны проявляться явно. Проверяй `null` для опциональных ссылок, внешних данных и состояний, где отсутствие значения ожидаемо.

## Unity Inspector и ассеты

- Связывай ассеты прямыми сериализуемыми ссылками и назначай общие ссылки у общего владельца. Для собственных ассетов в `Resources` и их загрузки через `Resources.Load`, `Resources.LoadAll` или `Resources.LoadAsync` требуется явное согласование. Для встроенных ассетов Unity допустим `Resources.GetBuiltinResource`.
- Добавляй `[Header]` к сериализуемым полям, когда он помогает разделить группы в Inspector.
- При перемещении ассетов сохраняй соответствующие `.meta`-файлы и GUID.

## Работа с Unity

- Используй Unity MCP только по прямому запросу пользователя. Это правило распространяется на чтение состояния Editor, сцен и Console, изменение объектов и ассетов, запуск Play Mode и тестов.
- Для автоматизации Unity Editor используй только Unity MCP. Не используй Computer Use, CUA, UI Automation или другие средства управления интерфейсом компьютера, включая получение списка окон и снимков экрана.
- Если нужный Unity MCP отсутствует или не подключён к нужному Editor, сообщи об этом и останови зависимую работу. Можно продолжать независимую работу с кодом и документацией. Прямая правка YAML и автоматически выполняемые Editor-скрипты не заменяют Unity MCP.
- По умолчанию не читай YAML сцен и префабов и не назначай ссылки в Inspector. Меняй сцены и настройки проекта в рамках прямого поручения. При согласованном использовании Unity MCP можно изменять префабы в рамках порученной реализации. Предпочитай правку общего префаба и сохраняй GUID, ссылки, наследование и требуемое поведение потребителей.
- Если для реализации нужны отсутствующие сведения из сцены или Inspector, запроси их у пользователя.

## Тестирование и проверка

- Проверку в Unity Editor и на устройстве выполняет пользователь. Запускай Play Mode, Unity Test Runner и проверки через Unity MCP только по его прямому запросу.
- После изменения C# перечитай затронутый код и выполни доступные быстрые статические проверки. Для полей Inspector проверь атрибуты и сериализуемые типы.
- Различай проверку кода, компиляцию и проверку поведения. Если требуется ручная проверка, укажи шаги, ожидаемый результат и то, что ещё нужно подтвердить.

## Git и существующие изменения

- Перед правкой проверь состояние рабочего дерева и сохрани несвязанные изменения пользователя.
- Для отката пользовательских изменений, удаления файлов или разрушительных Git-команд требуется явное подтверждение пользователя.
